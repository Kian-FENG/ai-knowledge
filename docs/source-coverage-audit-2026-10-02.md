## 已验证的采集与流程问题

1. **网页入口成功不等于新闻已采集。** `scripts/news.py` 的 `collect` 在 web 分支归档后直接返回；`landing_text` 仅为前 1,000 字符，原始 HTML 仍完整归档。正文采集依赖 Agent 后续 import。最近记录中 Qwen 仅提取到标题“Qwen”，Z.ai 也主要是产品首页标题。
2. **关注名单与每日覆盖没有强制关联。** `prompts/daily.md` 明确要求检查五个核心品牌并关注其他公司，这是已有 Agent 工作流程；但 `validate_editorial` 只检查 `source_checks` 的字段格式，允许空列表，也不要求所有核心公司及主题都有核查结果。结构校验通过不能证明覆盖完成。
3. **arXiv 有已发生的截断。** 最近完整采集的 313 个候选在每源 60 条上限下截断 253 条；随后以 500 上限补齐本次列表。每日提示词仍使用 `--limit 60`，仅靠提醒 Agent 补读，未来仍可能漏掉候选。RSS 自身也没有完整回溯保证。
4. **模型能力证据不够多样。** 没有模型卡、独立评测和方法更新的稳定来源；用公司公告可以描述官方声称，不能单独得出跨公司能力排名。
5. **编辑范围与样例不同。** 当前报告以北京时间 08:00 划分 24 小时，最多 24 个去重事件。样例共 50 条标题且正文含多日材料。`collect --days 14` 是候选回看范围，并不使日报收录 14 天新闻。渠道补齐后仍不应以复刻样例条数作为验收标准。

## 补齐优先级与验收

以下是待实施建议，本次审计没有修改来源配置或采集代码。

**P0：先补产业情报缺口。** 增加媒体发现层，覆盖中英文人事、融资、并购、IPO、商业合同和新公司。优先评估样例已经引用的 Reuters、Bloomberg、The Information，以及中文产业报道渠道；TechCrunch、36氪等作为候选补充。对未实测的站点先做接入验收，记录公开全文/订阅可读/仅摘要/失败状态。报道保留媒体归因；再查公司、投资方、交易对手或法定披露，不把传闻转成已发生事实。

**P0：补企业与供应链的一手渠道。** 核心公司的新闻、产品更新、定价、模型卡分别跟踪；集团业务与模型研究品牌分别跟踪。供应链按 NVIDIA/AMD/Qualcomm/AWS/Google、Huawei/寒武纪等计算平台，Samsung/SK hynix/Micron 等存储，TSMC/ASML 等制造设备分组；同时建立政策与司法公告组。这里只给出待评估主体，并未测试全部站点。

**P0：完成网页文章采集与覆盖验收。** 将“发现链接→正文与日期→归档→核查记录”做成可重复步骤；动态页面明确浏览器回退。每天每个必查主题和核心公司必须输出 checked/failed/not-checked，记录入口、检查时间和范围；允许出具覆盖受限报告，但不能把未检查显示为无新闻。避免仅增加 YAML URL 数量。

**P1：扩大技术与独立证据。** 增加模型卡、评测机构、更多 arXiv 分类和社区博客/关键开发进度；对论文做跨分类去重，按窗口补齐截断候选，保留分页/上限造成的缺口。技术性能归档基线、硬件、精度、负载、版本和测量主体。

验收以五项为准：能否发现具体文章、取得足够正文、核对发布时间、留下原始来源与运行记录、在失败/截断/未查时明确报告缺口。可连续运行若干日报窗口，与一份有原文 URL 且去重的人工基准比较事件召回；本样例需要先补原文和事实核查才能充当基准。
